# На чём строить drafta.org дальше

Написано 24.09.2026. Контекст: к лендингу нужно добавить документацию, формы и отзывы. Сайт при
этом должен продавать, хорошо индексироваться и не терять в скорости.

## Где сайт сейчас

Сейчас это 10 статических HTML-страниц (EN и RU). У них общие `tokens.css` и `site.css`, есть
немного JS для форм аккаунта и тарифов, всё раздаётся с Cloudflare Pages. По Lighthouse
Performance 94–100, SEO 100, около 230 KiB и 16–18 запросов на страницу. Это отличная база, и
главное — её не испортить.

Проблема не в скорости, а в поддержке:
- `<head>`, шапка и подвал скопированы в 10 файлов;
- каждая правка делается дважды, для EN и RU (аудит нашёл, что они уже начали расходиться);
- sitemap, hreflang и `noindex` приходится вести руками;
- документацию в чистом HTML писать и сопровождать дорого.

## Рекомендация: Astro + Starlight, документация на `drafta.org/docs/`

**[Astro](https://astro.build)** собирает сайт в статический HTML. По умолчанию на страницу не
уходит ни одного килобайта JS. Интерактив подключается «островами», только там, где он нужен.
Для продающего сайта с SEO это лучшее соотношение, потому что поисковик видит готовый HTML, а не
пустую страницу, которую достраивает JS.

**[Starlight](https://starlight.astro.build)** — официальная тема документации для Astro. Из коробки
в ней есть:
- навигация и поиск ([Pagefind](https://pagefind.app), статический, без сервера);
- i18n с переключателем языков и hreflang;
- «Редактировать на GitHub», тёмная тема, оглавление страницы;
- страницы из Markdown/MDX.

Контент документации уже подготовлен в этом формате: `content/docs/`.

**Путь `/docs/`, а не поддомен `docs.drafta.org`.** Поисковики считают поддомен отдельным сайтом, и
ссылочный вес документации не работает на основной домен. Подпапка собирает весь вес на
`drafta.org`, а переход «лендинг → документация» остаётся на одном сайте. В одном репозитории на
Astro это даже проще, чем поддомен.

### Как ложатся будущие задачи

| Задача | Решение |
|---|---|
| Документация | Starlight по пути `/docs/`, EN и RU, поиск Pagefind |
| Регистрация, вход, checkout | Остаются статическими страницами. Существующие `forms.js` и `plans.js` переносятся как есть, API — тот же `api.drafta.org` |
| Отзывы | Коллекция контента (`src/content/reviews/*.md`), которую модерирует владелец. На сайт попадает только одобренное, и это обычный HTML, который индексируется. Форма «оставить отзыв» — остров, который шлёт в API |
| Changelog и блог | Коллекции контента. CHANGELOG можно подтягивать из репозитория приложения на этапе сборки |
| SEO | Один компонент `<Seo>`: title, description, canonical, hreflang, OG и JSON-LD `SoftwareApplication`. Плюс `@astrojs/sitemap`. `noindex` для служебных страниц задаётся флагом во front-matter |
| `appcast.xml` | `public/appcast.xml`, `release.sh` пишет туда |
| Хостинг | Остаётся Cloudflare Pages: `npm run build`, выходная папка `dist/` |

### Почему не другие варианты

| Вариант | Почему нет |
|---|---|
| **Next.js / Nuxt / SvelteKit** | Хороши для приложений. Для маркетингового сайта они приносят рантайм JS (гидратацию) и серверную часть, которые не нужны, а в скорости и простоте хостинга сайт проиграет. Если когда-нибудь появится личный кабинет с большой логикой, его стоит делать отдельным приложением (например, `app.drafta.org`), а маркетинг оставить на Astro |
| **Hugo / Eleventy** | Тоже статические и быстрые. Но формы и интерактив пришлось бы собирать вручную, а готовой темы документации уровня Starlight с i18n и поиском у них нет |
| **Остаться на чистом HTML** | Разумно до релиза. С документацией, отзывами и блогом дублирование EN/RU начнёт стоить больше, чем миграция |
| **Docusaurus / VitePress на поддомене** | Отдельный стек, отдельный дизайн и хуже для SEO, чем подпапка |

### План миграции (после релиза 1.0)

1. `npm create astro`, затем:
   - `tokens.css` и `site.css` переносятся без изменений;
   - шрифты — в `public/assets/fonts/`, с `<link rel="preload">` для двух основных начертаний. Это
     убирает CLS 0,095, найденный аудитом.
2. Общий `BaseLayout` (head, шапка, подвал, переключатель языка) и компонент `<Seo>`.
3. Страницы переносятся 1:1. Тексты EN и RU выносятся в словари или в пары `.md`-файлов, чтобы
   структура была одна.
4. Подключить Starlight на `/docs/`, стиль подогнать под токены сайта: шрифты Lora, Golos и
   JetBrains Mono, акцентный цвет `--accent`.
5. Добавить `@astrojs/sitemap`, `robots.txt`, `404.astro` и редиректы через `_redirects`.
6. Сверить Lighthouse до и после. Критерий приёмки: Performance и SEO не ниже, чем сейчас.

Оценка: 2–3 дня на перенос существующих страниц без редизайна. Документация уже готова в Markdown.

## Что сделать до релиза, не дожидаясь миграции

Всё это делается правками статических файлов:
- `robots.txt`;
- `sitemap.xml` с `xhtml:link` hreflang для пар EN/RU;
- `404.html`;
- `<meta name="robots" content="noindex">` на login, register, verify и checkout;
- JSON-LD `SoftwareApplication` на главных страницах;
- мобильное меню навигации;
- `appcast.xml` (через `release.sh` после исправления переменной `APPCAST_PATH`);
- скриншоты вместо заглушек;
- переписанный раздел Security/FAQ (см. `Drafta/docs/audit/2026-09-24/README.md`).
